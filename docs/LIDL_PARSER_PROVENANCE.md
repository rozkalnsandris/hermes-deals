# Lidl parser provenance and runtime roles

## Canonical runtime graph

The machine-readable source of truth for Lidl parser and orchestration identity is:

`tools/lidl_parser_provenance/parser_runtime_graph.json`

It declares one canonical active parser adapter, every parser-capable Lidl
entrypoint, exact SHA-256 identities, import edges, immutable corpus bindings,
historical identities and retention rules. The backend regression suite runs
`verify_parser_runtime_graph.py` and fails closed when:

- a declared file changes without an explicit graph update;
- another canonical active adapter is introduced;
- an import edge no longer resolves to its declared target;
- an undeclared Lidl parser-capable file appears;
- a retired `parser.py` or `r6_parser.py` path is reintroduced;
- frozen evidence, parser hashes or corpus bindings drift.

## Declared roles

- `lidl_v631_runtime.py` — the only canonical active runtime adapter;
- `v631/r61_base.py` — frozen authoritative R6 base;
- `v631/r61_shadow.py` — frozen authoritative V6.3.1 shadow parser;
- `r61_base.py` and `r61_runtime.py` — reference-only compatibility evidence,
  not the active weekly parser path;
- `lidl_family_source_discovery.py` — selected family-store source discovery;
- `lidl_weekly_one_shot.py`, `lidl_weekly_staging.py` and
  `lidl-weekly-completeness.py` — guarded shadow/review entrypoints that resolve
  through the canonical V6.3.1 adapter;
- `lidl_corpus_import.py` and `lidl_review_seed_reconciliation.py` — immutable
  corpus and Review integration paths; they do not select a different parser.

The historical public `parser.py` identity and noncanonical `r6_parser.py` are
absent and have zero allowed importers. The former Codex V6.2 worktree remains
external evidence only and is not authoritative.

## Executable rescan adapter

The main repository contains the content-addressed loader at:

`tools/lidl_parser_provenance/lidl_v631_runtime.py`

It verifies both frozen source SHA-256 values before loading V6.3.1 and fails
closed on any drift. The OCR worker installs the pinned PyMuPDF dependency
through `backend/requirements-ocr.txt`.

The adapter was replayed against KW32 `scan-0003`; all 352 canonical parser
rows matched the archived observation exactly. This makes controlled rescans
reproducible, but it does not turn Lidl into an automatic production collector
and does not bypass corpus review or production gates.

Do not run a fresh Lidl corpus rescan from the old Codex worktree. It contains
the V6.2 rollback and is not authoritative.
